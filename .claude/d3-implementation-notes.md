## Design refinements decided at implementation time (supersede the architecture doc where they differ; they will be recorded as "écarts")
1. **Job validity by file, not version**: `MediaJob.sourceKey` = `Media.storageKey` at enqueue. A job's writes are valid only while `media.storageKey === job.sourceKey && media.deletedAt === null` and the job is still RUNNING and locked by this worker. Version bumps that don't change the file (poster replace/remove, focal point) never invalidate a job.
2. **Rendition keys independent of the version**: `variants/<mediaId>/rendition-<name>-<rand>.<ext>` (`renditionKey(id, name, ext)` in `server/lib/media/keys.ts`). No version column. Renditions are deleted (rows in the same transaction, files after commit) only when the FILE changes (`commitNewFile`, purge). Rendition URL = `/m/<id>/v<media.version>/renditions/<name>.<ext>` (ext = mp4|webm from `RENDITION_FORMATS`).
3. **Replacing an existing rendition** (a re-run with other settings) bumps the media version (immutable cache: new bytes never at an old URL), like a poster replacement (old version variants deleted). Creating a rendition that did not exist does not bump the version.
4. **Lossless rewrites** (`sanitize` = remove data tracks, `repair` = WebM duration/index) replace the original through the same path as "Optimiser": new version, old URLs 302, D2 preparation (keep-list + faststart) applied to the ffmpeg output, metadata re-analyzed by the D1 reader then `rewrites` merged in. The running job is carried over: its `sourceKey` is updated to the new key in the same transaction (it does not cancel itself).
5. **Server poster** only when `posterKey === null`, written with a guarded update (`posterKey: null, storageKey: job.sourceKey, deletedAt: null`), no version bump (first poster rule DD18), never overrides a user poster. Extracted from the H.264 rendition when it exists (SDR), else from the original with tone mapping when HDR.
6. **Converted formats** (MKV…): accepted only when processing is active (`acceptedMimeTypes(await videoProcessingActive())`). At upload: no D1 parsing; `width/height/duration = null`, metadata `{ container, videoCodec: null, audioCodec: null, codecs: null, hasAudio: false, rotation: 0, bitrate: null, faststart: null, hasLocation: false, playback: 'none', prepared: [], durationEstimated: false, dataTracks: [], hdr: null, rewrites: [] }`. The job's `probe` step fills width/height/duration and codec fields (same version, no bump). Original served with `Content-Disposition: attachment`. `sources[]` empty until the H.264 rendition exists.
7. **"Processing active"**: `mode === 'embedded'`, or `mode === 'external'` and a worker presence row (`Setting` key `videoWorker:<id>`, `updatedAt`) seen within `WORKER_SEEN_WINDOW_MS`. Async `videoProcessingActive(): Promise<boolean>` cached 30 s (`server/lib/video-processing/status.ts`). `mode === 'off'` → never active, `processingState` stays null on new uploads and no job is created.
8. **Hold (503)**: `/m/` original and renditions answer `503 PROCESSING_PENDING` + `Retry-After: 30` + `Cache-Control: no-store` when `deliveryHeld(media, settings.mode)` and the access is not `signed` with scope `admin`. Checked after `authorizeDelivery`, before the 304 check. Posters/derivatives/tracks are never held.
9. **Light polling endpoint** (not in the doc): `GET /api/admin/media/:id/processing` → `{ version, processingState, processing }` so the detail page can poll every 5 s without a full refresh (which would reset forms and re-sign URLs).
10. **Progress writes** (every ≥ 5 s) update only `MediaJob` (no `mediaChanged`); state transitions (PENDING→PROCESSING→READY/FAILED) go through the service and call `mediaChanged`.
11. **Trash** cancels active jobs (state kept); **restore** re-enqueues when processing is active and state is not READY; **duplicate** copies renditions (storage.copy + rows) and `processingState`; if the source is not READY and processing is active, the copy gets its own job; **purge** relies on cascade + `variants/<id>/` prefix.
12. Module names: new code under `server/lib/video-processing/` (never reuse `server/lib/media/processing.ts`, which is the sharp/images semaphore).

## Additional decisions for Module D
1. **Priority of held media**: when a video is enqueued and its D1 metadata has `dataTracks.length > 0` (public delivery held, e.g. most iPhone videos with `mebx`), use priority `10` (ahead of normal 0 and backfill -10), so the GPS removal is not stuck behind long transcodes. Within the job, `sanitize` runs first and its commit (new version without data tracks) lifts the hold before any transcode.
2. **State transitions**: enqueue → `PENDING`; claim → `PROCESSING` (guarded by storageKey = sourceKey; `mediaChanged`); success → `READY`; definitive failure → `FAILED`; retryable failure → back to `PENDING` with `runAfter`; cancel (trash/replace) → state left as is for trash (restore re-enqueues), replaced by the new job's PENDING for a replacement. A cancelled job never writes the media state.
3. **Retry semantics**: transient errors (TIMEOUT, CONVERSION_FAILED from a crash/signal, storage errors, lost lease) retry with `retryDelay(attempts)`; deterministic ones (NO_VIDEO_TRACK, UNREADABLE from ffprobe on a stable file, TOO_LONG, SOURCE_MISSING after a fresh read) fail at once. `FFMPEG_UNAVAILABLE` on a worker: requeue without consuming an attempt and stop that runner (the worker is misconfigured), log loudly.
4. **Lease loss / cancellation**: the heartbeat (every 30 s) renews with `where { id, lockedBy, status: 'RUNNING' }`; count 0 → abort the AbortController → ffmpeg killed → nothing written. Every commit re-checks validity inside its guarded write.
5. **Re-run ("Relancer") semantics**: `requestProcessing(media)` creates a new job for the current file (cancels any active one), `existing` passed to the plan is `[]` so renditions are redone; replacing an existing rendition bumps the version (refinement 3). Allowed for FAILED and READY (and null state when active = first processing of an old video).
6. **Rendition commit**: write file to storage (`renditionKey`), then in one guarded transaction upsert the `MediaRendition` row (by mediaId+name) only if `media.storageKey === job.sourceKey && deletedAt null && job still RUNNING by this worker`; if an older rendition existed → version bump + `deleteVersionVariants` semantics for the old version's derived images (the poster derivatives are tied to the version string) and delete the old rendition file after commit; if the guarded write fails → delete the new file.
7. **Converted formats probe commit** (`applyProbeResult`): fill `width/height/duration` and metadata codec fields (`videoCodec`, `audioCodec`, `hasAudio`, `rotation`, `bitrate`, `hdr`, `codecs` null) without version bump, guarded by storageKey; also set `hdr` for playable containers (metadata only). Keep `playback: 'none'` for converted containers.
8. **Worker identity**: `<hostname truncated>:<pid>:<8 random hex>` ≤ 191 chars.
9. **Embedded mode in dev**: Nitro dev runs in a worker thread and reloads on file changes: the close hook must kill ffmpeg and release jobs on every reload.
10. **Tests**: `tests/video-queue.test.ts` with an in-memory fake store for claim/lease/reap/retry/cancel/catch-up logic and the runner loop (injected clock/sleep), plus pure tests of state-transition decisions. Keep tests deterministic and fast.
